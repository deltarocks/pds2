= Version migrations
:order: 1

bungeeoxide (`crates/bungeeoxide-converter`) keeps one schema per protocol
version and the migrations between them:

[cols="1,3"]
|===
| Path | Contents

| `minecraft.pds` | the root schema: a package per version, in version order, and the `migrations` definition
| `pds/<version>.pds` | the schema of a version. `just update` regenerates every release minecraft-data has, headed by `@!doc` (source commit, Minecraft versions served), `@!protocol [...]` and `@!snapshots [(protocol: ..., name: "..."), ...]`. A schema lists the snapshots numbered from `0x40000000` (written in decimal) of the releases it serves: the release in the snapshot's name, or for weekly names the next release by data version, or for April Fools builds off the data version line the release of the build before them. Snapshots of a release no schema serves yet go to the latest schema. Versions minecraft-data lacks are written by hand next to them, with their own `@!protocol` (`@!legacy_protocol` for pre-netty numbers, which collide with netty ones).
| `minecraft-data.commit` | the minecraft-data commit `just update` reads; `just bump` moves it to upstream master
| `minecraft-data.pins` | data folders read from another commit, one `<folder> <commit> <source>` line each (tab separated), for versions only an unmerged minecraft-data branch has
| `patches/<path>` | fixes to minecraft-data files, `<path>` mirroring the file in minecraft-data: a file or a directory of files applied in name order, RFC 6902 `.json` patches for JSON (guarded by `test` operations) and unified `.patch` diffs for text. A patch can create a file minecraft-data lacks.
| `data/` | registries extracted by `just update`: block states, items, entities, particles, sounds, vanilla registry codecs
| `migrations/<old>-<new>.pds` | rules converting between adjacent versions
| `migrations/every.pds` | hooks applied in every step
| `migrations/<old>-<new>.diff.txt` | definitions that changed between them, from `just diff`
|===

[source,pds]
----
@!deduplicate true

package(v1_8) {
    @!doc "Minecraft 1.8 protocol types"
    include("pds/1.8.pds");
};

package(v1_9) {
    @!doc "Minecraft 1.9 protocol types"
    include("pds/1.9.pds");
};

package(convert) {
    migrations(virtual: true) {
        version(v1_8, name: "1.8");
        version(v1_9, name: "1.9") {
            include("migrations/1.8-1.9.pds");
        };
        every {
            include("migrations/every.pds");
        };
    };
};
----

Every version is a package, so `just gen` compiles a crate per version
(`bungeeoxide-minecraft-v1-8`, ...), and `@!deduplicate` keeps one copy of
what versions share: a definition lives in the first version that has it and
later versions re-export it (see
xref:../language/definitions.adoc[Definitions]). Natives sit at the top level,
in `bungeeoxide-minecraft-root`.

`migrations` comes from `pds2-specializer-minecraft-data`. It lists the
versions in order: `version(package, name: "...")` names a version's package
and its name, and its block holds the rules of the step from the previous
version, here included from the migration files. The protocol numbers are the
package's `@!protocol`, `@!legacy_protocol` and `@!snapshots`, which the
included schema brings. `step: false` leaves the step from the previous version out, and
`every` holds the hooks of every step. A schema has one `migrations`; the
package holding it is written with `--module convert=src/gen/convert.rs`, so the
generated `convert` module lands in the crate that has `crate::custom` and
`crate::Session`. It has one step per pair of adjacent versions, in both
directions (`up` = older to newer, `down` = newer to older). Converting across
several versions chains the steps. To add a version, `just update` writes its
schema; add its package and its `version` to `minecraft.pds`, then run `just
scaffold`.

Identical types pass through untouched. Containers are matched field by field
and unions arm by arm, by name, so renumbered packets and moved fields need no
rules. A field, arm or list element that both versions pass the same argument
with different values (a list counted by another field, a union switched on
another tag) is not converted by itself: its layout depends on that value.
Everything else must be written down in the step's migration file,
otherwise generation fails listing each missing rule; rules that end up unused
are errors too. A step marked `step: false` is not generated:
`STEPS[i]` tells whether the step from version `i` to `i + 1` exists, and
`reachable(a, b)` whether every step between two versions does.
`version_of(protocol)` maps a protocol number to its version index and
`legacy_version_of` a pre-netty one; `Version` names every version
(`Version::V1_8`) and indexes tables directly. `SNAPSHOTS` holds `(protocol,
name, version)` for every snapshot, sorted by protocol, and
`snapshots_of(protocol)` returns the entries of one number: usually one, none
for an unknown number, and several where snapshots share a number, possibly
listed under different versions. A snapshot number that is also a release
number, or a snapshot listed twice, is an error. `packet_name(root, version,
bytes)` reads only the packet id.

For hand-written code `convert` also has a module per version that has a
step, re-exporting each type that version uses under its unversioned name:
`convert::v1_8::slot`, `convert::v1_9::play_toClient_packet`. Types without a
name of their own are reached through their owner: `__field`, `__arm` and
`__items` for list elements, as in
`convert::v1_8::play_toClient_packet_spawn_entity__velocity`. These names stay
the same when other versions join.

[source,pds]
----
updated(entityMetadata, up: custom(metadata_1_10), down: custom(metadata_1_9_4));

namespace(play) {
    namespace(toClient) {
        updated(packet) {
            removed(map_chunk_bulk, up: custom(map_chunk_bulk_1_9));
            renamed(scoreboard_team, to: teams);
            added(boss_bar, down: drop);
            converted(keep_alive);
        };

        updated(packet_entity_teleport) {
            converted(x, up: f64(./x) / 32.0, down: i32(./x * 32.0));
        };

        updated(packet_map) {
            added(trackingPosition, up: true);
        };
    };
};
----

`updated(name)` names a definition by its path inside the version's package,
or a field or arm when nested. A definition that only names a list or an
option (`def(ids) => array(Count: varint) => varint;`) has no type of its own,
so its rules go where it is used, under the field or arm holding it. Inside
`updated`:

[cols="1,3"]
|===
| Rule | Meaning

| `added(x, up: ...)` | `x` exists only in the newer version; `up` computes it. Arms take `down` instead, to handle the arm when going down.
| `removed(x, down: ...)` | `x` exists only in the older version; `down` computes it (arms: `up`)
| `renamed(old, to: new)` | the same field or arm under another name
| `converted(x, up: ..., down: ...)` | the type of `x` changed; without `up`/`down`, a numeric cast
| `hooked(x, down: custom(f))` | `f` rewrites `x` in place before the step converts it (`up:` for the other direction); see below
| `updated(x) { ... }` | rules for a nested field or arm
|===

An action is one of:

* an expression over the source value: `./field`, `self` for the whole
  value, casts (`f64(./x)`), arithmetic, records (`(a: 1, b: ./c)`), lists and
  union symbols. On a union arm, `self` and `./field` read the arm's payload;
* `custom(fn)`, calling `crate::custom::fn`;
* `drop`: inside a list the element is left out, inside an option it becomes
  empty, anywhere else the packet is not sent;
* `default`: an arm becomes the target union's payload-less `default` arm with
  the same tag;
* `unsupported`: conversion fails at runtime.

`converted(items)` casts list elements whose numeric type changed.
`updated(name, up: ..., down: ...)` with actions replaces the whole conversion
of a type, also for types that did not change shape: identical types pass
through untouched otherwise, so a byte buffer whose format changed or ids that
were renumbered need such a rule. A file may update the same definition in
several blocks; they are merged. Custom functions get `&mut crate::Session`:
`cx.state::<T>()` keeps per-module state across packets, and `cx.send(root,
version, bytes)` queues a packet for the other direction (a serverbound
conversion answering the client, for example), which the caller converts from
that version and delivers. `cx.send_model(root, version, model)` queues a
carried model the same way; once the caller has given the session its versions
with `set_versions(server, client)`, `take_outgoing` converts such models
straight to that version, otherwise it encodes them where they were queued.

[cols="1,3"]
|===
| Rule position | Signature

| field | `fn(source: &SourceContainer, cx) -> Result<Field>`
| packet arm | `fn(payload, cx) -> Result<Vec<TargetPacket>>`
| whole type | `fn(value: Source, cx) -> Result<Target>`
| hook | `fn(value: &mut T, from: usize, to: usize, cx) -> Result<()>`
|===

A hook names a field or arm holding a leaf value: a string, a native such as
`anonymousNbt`, or an option or list of them. Its function gets the value of
the version the step starts from, with both version indices, and may rewrite
it; the step then converts the rewritten value with its other rules. Where `x`
holds a container or union, or does not exist, the hook is skipped. Hooks
nested under `updated` blocks run together, as one prologue of the type that
owns the outer `updated`, before any of its rules, `custom` ones included. So
a hook placed under the packet union (`updated(packet) { updated(chat) {
hooked(message, ...) } }`) runs even in steps that convert that packet arm by
hand.

`every` holds hooks that apply to every step, written like a step but with
`hooked` and `updated` rules only. Each step merges them
into its own rules wherever the named definitions, fields and arms exist in
its source version; a step only has to convert a type because of them in the
hook's direction. A rule of `every` that no step uses is an error.
bungeeoxide uses it to translate text keys an older client
does not know (`custom::localize`, see `languages`).

The crate's `Justfile` drives the work:

[cols="1,3"]
|===
| Recipe | Does

| `just gen` | compiles `minecraft.pds` into the version crates in `minecraft/` and the `convert` module, adds new crates to the workspace and runs the tests
| `just scaffold` | creates missing migration files and appends a rule for every structural difference: `drop` for packets one side lacks, `unsupported` where a conversion has to be written. Rules it added that turn out unused are removed again. The files have to be included from `minecraft.pds` already.
| `just languages` | downloads the English strings of every version (minecraft-data `language.json`, through `minecraft-data.commit` and `patches/`) into `target/minecraft-languages/<folder>.json`, with `index.tsv` mapping version names to folders; `just update` runs it too. Mojang's text stays out of git.
| `just report [from] [to]` | replays recorded 1.8 server traffic one step at a time, decoding the result at every version, and lists what each step drops or fails
|===

`pds2 compile ... --check` reports missing and unused rules without writing
anything. `migrations(virtual: true)` lets custom code carry packets through
the steps as decoded models instead of bytes: `convert` asks
`crate::custom::virtual_start` whether to take a packet over, advances such
models with `virtual_step` and encodes them once with `virtual_finish` at the
target version. Before a step converts bytes, `virtual_wire` may take them over
and return models or bytes in their place. `convert::inspect(root, version,
bytes)` decodes bytes as a version's packet and names it.

`src/registry` reads minecraft-data registries kept in `data/` (written by
`just update`): block states, items, entities, particles, sounds and the
vanilla join game / registry codec. `remap_state` and `remap_name` move ids
between versions by name, with renames listed in `registry/renames.rs`;
`legacy_block` and `legacy_item` translate pre-1.13 `id:meta` pairs.
Tables are built once per version pair and read without locks.

`languages` reads the cache of `just languages` lazily, on the first text that
needs it: `languages::load(dir)` names the directory, `languages::install`
puts in a ready table (tests build small ones with `Languages::new`). Versions
older than the oldest language (1.6.x) use its keys. Every step going down
turns `translate` components whose key the older version's language lacks
into literal text with the English pattern (or the component's `fallback`)
applied to the arguments, keeping styles and events; keys no language has
stay, unless a `fallback` has to stand in below 1.19.4. Text without
`"translate"` is not parsed. Text flattened to legacy strings (chat before
1.6, kicks before 1.7, signs for 1.7, item names and scores before 1.13)
renders every key. Without the cache, keys pass through and flattening knows
a dozen chat keys.

Chat typed by a `chat_type` id (1.19+) becomes plain chat in the steps whose
older side cannot show it (1.19.3 to 1.19.2, 1.19.2 to 1.19, 1.19 to 1.18.2,
and inline chat types from 1.21.1 to 1.20.5). Those steps keep the chat type
registry of the login that passed through them (falling back to the vanilla
one) and render the entry's decoration as vanilla clients do: its translation
key with the `sender`, `target` and `content` parameters and its style, so
data pack chat types work too. The rendered text goes through the same
translation fallback.
